## 1. 背景（確定事実。再検討・再調査は不要）

- 本組織の方針として、すべての SSoT は GitHub に置く。Backlog 上の文書はコピーであり正本ではない。
- Backlog の「ドキュメント」機能は Mermaid / PlantUML / LaTeX を描画する。旧「Wiki」機能は Mermaid を描画しない。
- Backlog ドキュメント API は 追加（POST、content は Markdown 形式）・取得（GET、plain と json を返す）・
  削除は提供されているが、更新 API は提供されていない。
- GitHub の Markdown は Mermaid をネイティブ描画するが、PlantUML は描画しない。

## 2. 決定事項（これを規範文として書き起こす）

RFC 2119 / 8174 の助動詞は、本リポジトリの既存標準の用法に合わせること。

| ID | 決定 | 強度 |
|----|------|------|
| D-1 | 文書・図の SSoT はバージョン管理下のリポジトリに置く。外部ドキュメントツール上の文書は派生コピーであり、正本として扱ってはならない | MUST / MUST NOT |
| D-2 | 図はソース（テキストまたは編集可能なソースファイル）をリポジトリ内に保持する。レンダリング済み画像のみを成果物として保持してはならない | MUST / MUST NOT |
| D-3 | 論理図（シーケンス・状態遷移・フロー・ER・C4 コンテキスト相当）は Mermaid で記述する | MUST |
| D-4 | クラウド物理構成図（ネットワーク境界の入れ子とサービス識別アイコンが情報の主要部を担う図）に Mermaid を用いてはならない | MUST NOT |
| D-5 | 物理構成図のレンダリングは CI 上で決定的に行う。レンダリング時に外部ネットワークから素材を取得してはならない（アイコン素材はバージョンを固定して vendoring する） | MUST / MUST NOT |
| D-6 | 外部ツールへ複製する文書は front matter で明示的に opt-in する。既定は非複製とする | MUST |
| D-7 | 複製されたコピーには、出所リポジトリ・ソースパス・生成元 commit SHA・生成日時・当該コピーが編集禁止である旨を、機械可読な形で含める | MUST |
| D-8 | 正本とコピーの乖離を機械的に検出する手段を持つ | SHOULD |
| D-9 | 安定 URL を要求される入口文書は、自動再生成の対象から除外する | SHOULD |

### D-3 / D-4 の根拠（ADR の「決定理由」に書くこと）

- D-3: Mermaid は GitHub と Backlog ドキュメントの双方がネイティブ描画する唯一の記法であり、
  同一ソースを中間生成物なしで両方に供給できる。PlantUML は Backlog では描画されるが GitHub では描画されず、
  ビルドステップが非対称に発生する。
- D-4: (1) Mermaid のクラウド用アイコンは実行時の registerIconPacks() 登録に依存し、
  ホスト型レンダラでは機能しない。(2) architecture-beta は固定グリッド上に構築されエッジルーティングを
  持たないため、ノード数がおよそ 8 を超えるか関係が交差する構成で可読性が破綻する。
  (3) Region / VPC / AZ / Subnet / セキュリティ境界のような多段の入れ子を安定して表現できない。

## 3. 未検証事項（「検証済み」と書いてはならない）

次は未検証の前提である。規範文中で確定事実として記述せず、
governance/enforcement-ledger.md に未整備／整備中として明示的に登録すること。

- U-1: Backlog のドキュメント追加 API の content に Markdown の ```mermaid フェンスを含めた場合、
  ドキュメント上で言語指定付きコードブロックとして復元され、描画されるか。
  ドキュメント本文は構造化表現（json フィールド）で保持されるため、Markdown パース時に
  info string が言語指定として保持されるかどうかに依存する。これが本方式全体の前提条件である。
- U-2: 更新 API が存在しないため、複製の更新は削除＋再作成となり documentId が変化する。
  パーマリンク・コメント・タグへの影響範囲。
- U-3: 取得 API が返す plain フィールドの正規化方法（乖離検出のハッシュ比較に使えるか）。

U-1 が未検証である間は、複製自動化の実装（CI ジョブ・スクリプト）を行ってはならない。

## 4. 作業単位

WU ごとにコミットを分け、1コミット1関心事とする。

### WU-1: 技術標準の新設

standards/ に図表記法と外部公開の標準を新設する。WU-0(c) の判断に従って配置する。

- D-1〜D-9 を rule ID 付きの規範文として記述する
- 各ルールに検証方法（機械検証可能か、可能なら何を検査するか）の欄を設ける。
  機械検証できないルールは「人手レビュー」と正直に書き、検証可能であるかのように書かない
- D-3 / D-4 の適用境界（どの図がどちらに該当するかの判定基準）を、
  レビュー時に判定が割れない粒度で書く

### WU-2: ADR

adr-rules.md に従い、2本起票する。1本にまとめない。

- ADR-a: 図表記法の選定 — 採用案（論理図＝Mermaid／物理構成図＝CI レンダリング）と
  却下案を必ず記載する。却下案には最低限、次を含め、それぞれ却下理由を書くこと。
  - 全図を Mermaid で統一する案
  - 全図を PlantUML で統一する案
  - 全図を draw.io で統一する案
  - 作図 SaaS（Cacoo 等）に寄せる案
- ADR-b: 外部ドキュメントツールへの複製方式 — SSoT を Git に置き外部ツールをコピーとする決定、
  および更新 API 不在に起因する制約（削除＋再作成、ID 揮発）とその受容理由。
  却下案として「外部ツールを SSoT とする案」「複製せずリンクのみとする案」を記載し、
  後者を却下する場合は読み手が正本にアクセスできない層であるという前提を明示すること。

### WU-3: 運用手順

playbooks/ に複製手順を追加する。U-1 が未検証である現時点では手動手順として記述し、

### WU-4: 強制台帳への登録

- D-1〜D-7 のうち機械検証可能なもの → status は既存語彙に従う
- D-8（乖離検出ゲート）→ 未整備として登録し、U-1 の解消を前提条件として記載
- 台帳に「整備済み」と書けるのは、実際に task verify から実行される検査が存在する項目のみ

> **実装上の追記（2026-09-05 の実行で判明）**: D-1〜D-9 はいずれも本 WU の範囲では機械検証を
> 実装しない（新規の scripts/checks/*.sh を追加しない）ため、追記する台帳行はすべて人間ゲートの
