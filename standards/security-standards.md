# セキュリティ標準（Security Standards）

* Version: 0.3.0（Proposed / ドラフト）
* Date: 2026-08-20
* 上位規範: constitution.md（開発憲章）

本書は、憲章「Security by Default」「データ保護とAI入力境界」「依存関係とサプライチェーン」が委譲する詳細基準の正本（SSoT）です。憲章と矛盾する場合は憲章が優先します（MUST）。本書は standards/ai-governance.md と併用します。

---

## 1. データ機密区分（Data Classification）

すべてのデータは次のいずれかの区分に分類しなければなりません（MUST）。区分が未定義のデータを扱う機能を本番反映してはなりません（MUST NOT。憲章「データ保護とAI入力境界」）。

| 区分 | 定義 | 例 |
| --- | --- | --- |
| Public | 公開済み・公開可能 | 公開ドキュメント、OSS |
| Internal | 社内限り。漏洩しても限定的影響 | 社内設計、非機密ログ |
| Confidential | 機密。漏洩で重大な影響 | 事業計画、非公開コード、顧客名 |
| Restricted | 最重要。法規制・契約で保護 | 個人データ(PII)、認証情報、決済情報、顧客機密 |

---

## 2. AI 入力境界マトリクス（憲章「データ保護とAI入力境界」の正本委譲先）

本番由来データの AI／外部 AI への入力可否は次のとおりです。**構造的強制を第一とし**、AI には本番の Confidential / Restricted へ到達しうる接続権限を付与してはなりません（MUST NOT）。

| 区分 | ローカル/社内 AI | 外部 AI サービス |
| --- | --- | --- |
| Public | 可 | 可 |
| Internal | 可（SHOULD: 必要最小限） | 原則不可（要承認・契約上の保護が前提） |
| Confidential | 不可（MUST NOT） | 不可（MUST NOT） |
| Restricted（PII 等） | 不可（MUST NOT） | 不可（MUST NOT） |

* 開発・検証には匿名化／マスク済み／合成データを使用するべきです（SHOULD）。
* Restricted/Confidential を収集・記録（ログ含む）・送信しうる実装に着手する時点で、本マトリクスと standards/ai-governance.md に照合しなければなりません（MUST）。判断不能なら人間に諮る（MUST）。

---

## 3. 秘密情報（Secrets）

* 秘密情報（認証情報・APIキー・トークン等）をソースコード／設定ファイルにハードコードしてはなりません（MUST NOT）。
* シークレットスキャンを CI で実施し、検出時はマージ不可とします（MUST。憲章8章）。
* 秘密情報はシークレットマネージャ等で管理し、最小権限で参照します（SHOULD）。

---

## 4. 個人データ（PII）の取り扱い（憲章の委譲先）

* 収集の最小化、保存期間の定義、利用目的の制限を遵守しなければなりません（MUST）。
* 適用される法令・規制（例: GDPR / 個人情報保護法等）を識別し文書化しなければなりません（MUST。正本は governance/ または本書）。

---

## 5. 脆弱性の重大度基準（憲章「依存関係」の委譲先）

* 深刻度スケールは CVSS v3.1 以降を用います。
* **「重大」の閾値: CVSS 7.0 以上（High / Critical）**。既知の High / Critical 脆弱性を含む依存をマージしてはなりません（MUST NOT。憲章8章）。
* **機械強制の適用範囲（2026-08-24 明示。外部レビュー指摘）**: 上記 MUST NOT のうち機械強制（`scripts/checks/deps.sh`）が失敗させるのは、**上流に修正版が存在する**脆弱性に限ります（`--ignore-unfixed`）。修正版の無い脆弱性で恒久的に赤くなるとゲートごと外される力学が働くための運用上の選択ですが、その結果として**修正版の無い High / Critical は本ゲートでは検出されません**。この差分は強制台帳 #2 にも開示します。修正版の無い重大脆弱性の受容可否は、人間ゲート（不可避）(b) として PR レビューで判断しなければなりません（MUST）。回避策（当該依存の除去・代替・機能無効化）の検討を伴わずに受容してはなりません（MUST NOT）。
* 依存脆弱性スキャンを CI で実施します（MUST）。自動更新（Renovate / Dependabot 等）で継続保守します（SHOULD）。

## 6. サプライチェーン完全性（SLSA / SBOM）

* 本番成果物は SBOM を生成し、出所（Provenance）を検証可能にするべきです（SHOULD）。形式は SPDX または CycloneDX。
* 供給網完全性レベルの目標: **SLSA Build L2 以上**を目標とするべきです（SHOULD。組織が確定）。
* 本番利用する依存・成果物は本番利用判定（ライセンス・既知脆弱性・保守状況・出所）を通過するべきです（SHOULD）。
* **ランタイムの LTS 追随**: Node.js 等のランタイムは **Active LTS** を追跡するべきです（SHOULD）。
  Maintenance LTS へ移行した時点で次期 LTS への更新を計画し、EOL 到達前に完了させるべきです（SHOULD）。
  採用版は `.mise.toml` を正本とします。
* **バージョンレンジの上限**: 依存宣言には上限を設けるべきです（SHOULD）。上限のないレンジ（例: `>=10`）は
  上流のメジャー更新を無警告で取り込み、再現性を損ないます。更新は意図的な変更として扱います。

### 6.1 ライセンス互換性（憲章「6.」承認マトリクス 理由区分 (c) の委譲先）

本節は、依存関係のライセンスが自組織の配布形態・契約と両立するかの判定基準を定めます。

constitution.md「6.」承認マトリクスは「依存関係の新規追加、およびメジャー更新・**ライセンス変更**を伴う更新」を理由区分 **(a)(c)**（(c) = 法令・契約・規制要求）として人間承認必須に置き、development-process.md「1.」はこれを **Class A** に分類しています。しかし 2026-08-24 まで、この規範に対応する行が強制台帳に**一行も存在せず**、機械検知の主体もありませんでした（外部レビュー指摘）。依存脆弱性（「5.」）が #2・#30 で二重に配線されているのと対照的に、規範だけがあって強制も開示も無い状態だったため、本節と強制台帳 #55 を新設して是正します。

* 依存関係のライセンス検査は、依存マニフェスト（`package.json` / `go.mod` / `pyproject.toml` / `pom.xml` / `Gemfile` / `Cargo.toml` / `composer.json` 等）を含む採用で実施しなければなりません（MUST。実装は `scripts/checks/deps.sh`）。マニフェストが存在しない採用では休眠し、追加時に活性化します（MUST。「8.」の SAST と同一パターン）。
* **ライセンス製品・チェッカのツール名は、本書および constitution.md に記載してはなりません（MUST NOT）。**「8.」の SAST と同一の方針です。実行コマンドは汎用・差し替え可能な機構（環境変数 `LICENSE_SCAN_CMD` / `scripts/dev/license-tool.sh` / `LICENSE_FAIL_SEVERITY`）で解決するべきです（SHOULD。実装は `scripts/checks/deps.sh` を正本とする）。
* **許可ライセンス・禁止ライセンスの一覧、および自組織の配布形態（SaaS / オンプレ配布 / ライブラリ再配布）に応じたコピーレフト条項の受容範囲は、本節では確定しません（`TBD-HUMAN`）。** これは法務・契約上の判断であり、AI が値を発明してはなりません（MUST NOT。憲章「10.1.3 推測の禁止」）。採用組織は ADR で確定し、本節へ反映してください。
* ポリシー確定までの間、ライセンス検査の合否判定を「整備済み」として扱ってはなりません（MUST NOT。憲章「8. ブートストラップ規定」）。`scripts/checks/deps.sh` は未配線である旨を毎回警告し続けます。
* ライセンスの**変更**（既存依存のライセンスが上流で変わる更新）は、新規追加と同様に Class A として扱わなければなりません（MUST。development-process.md「1.」）。なお現行のクラス分類はパスベースであり、`package.json` / `go.mod` 等はパス表の Class A に含まれないため、**ライセンス変更を含む依存更新 PR は機械的には Class C として扱われます**。この乖離は強制台帳 #55 に既知の限界として開示し、当面は人間ゲート（暫定）で担保します。

## 7. 認証・トークン・通信の準拠標準（IETF BCP）

該当技術を採用する場合、以下の Best Current Practice への準拠を既定とします。逸脱は ADR で理由を明記しなければなりません（MUST）。

* **OAuth 2.0**: BCP 240（RFC 9700: OAuth 2.0 Security Best Current Practice）に従わなければなりません（MUST）。特に、公開クライアントは認可コードフロー＋PKCE を既定とし、Implicit グラント・Resource Owner Password Credentials グラントを新規採用してはなりません（MUST NOT）。
* **JWT**: BCP 225（RFC 8725: JSON Web Token Best Current Practices）に従わなければなりません（MUST）。特に、`alg: "none"` を受理しない・検証アルゴリズムを明示固定する・`iss` / `aud` / `exp` を検証する（MUST）。
* **TLS**: BCP 195（RFC 9325: TLS/DTLS の推奨構成）に従うべきです（SHOULD）。TLS 1.2 未満を新規に有効化してはなりません（MUST NOT）。
* **脆弱性報告窓口**: インターネット公開サービスは RFC 9116（`security.txt`）で報告窓口を公開するべきです（SHOULD。リポジトリの SECURITY.md と整合させる）。

## 8. 第一者コードの静的解析（SAST）（憲章「8. 機械的に検証可能なルール」の委譲先）

本節は、第一者コード（自組織・AIエージェントが記述したソースコード）に内在する脆弱性クラス（インジェクション、XSS、安全でないデシリアライズ、安全でない暗号利用等）を対象とする静的解析（SAST: Static Application Security Testing）の基準を定めます。

「5. 脆弱性の重大度基準」はサードパーティ依存関係の**既知**脆弱性（CVE ベース）を対象とし、本節は自組織が書いたコードそのものに**内在する**脆弱性パターンを対象とします。検出対象・検出手法が異なるため、両者を同一基準に統合せず、**別項目として**扱います（MUST NOT 混同。constitution.md「8.」）。

また、standards/coding-standards.md「1. 整形・静的解析」が扱うフォーマッタ／リンタ／型チェックは、コードスタイル・型安全性の検査であり、本節が扱うセキュリティ脆弱性クラスの検出とは目的が異なります。両者を同一のゲートとして扱わないでください（両者はそれぞれ独立して合格を要します）。

* SAST は、第一者コードを含む変更（機械強制の対象。scripts/checks/sast.sh）に適用しなければなりません（MUST）。対象スタックが存在しない採用（コードを含まない採用）では休眠し、コード manifest（`package.json` / `pyproject.toml` / `go.mod` / `pom.xml` 等）の追加時に活性化します（MUST。休眠・活性化パターンは「10.1」の UI 領域と同趣旨）。
* **SAST 製品・ツール名は、本書および constitution.md に記載してはなりません（MUST NOT）。** ツール選定は ADR で行う対象であり（adr-rules.md、constitution.md「5. ADRポリシー」）、本節は能力要件のみを定めます。SAST の実行コマンドは、汎用・差し替え可能な機構（例: 環境変数、または `scripts/dev/` 配下の差し替え可能なラッパースクリプト）を通じて解決するべきです（SHOULD。実装は scripts/checks/sast.sh を正本とする）。
* 重大度スケール・カットオフ値は、採用する SAST ツールが出力する重大度分類に従います。**具体的な閾値・スコアリング方式は本節では確定しません**（`TBD-HUMAN`。governance/proposals/gp-0005-sast-gate.md「5. 未解決事項」）。ツール採用の ADR で、「5.」の依存脆弱性基準（CVSS 7.0 以上でマージ不可）と構造的に対称な設計（例: Critical / High 相当の検出でマージ不可）を確定するべきです（SHOULD）。カットオフ確定までの間、SAST 検出結果に基づく合否判定は整備済みとして扱ってはなりません（MUST NOT。憲章「8. ブートストラップ規定」）。
* 誤検出（false positive）の抑制（suppression）は、理由の記載を伴わずに行うべきではありません（SHOULD NOT）。抑制基準・記録方法は採用ツールの ADR で定めるべきです（SHOULD）。

### 8.1 SAST が構造的に検出できない欠陥クラス（検出限界の開示）

SAST は静的な構文・データフロー解析であり、次の欠陥クラスは**原理的に検出できません**。これらは constitution.md「3. 基本原則」検証手段の選択が定める人間ゲート（不可避）**(a) 意味的判断**（要求との一致・ビジネス不変条件・認可の意図）に該当し、機械検証への移行対象ではありません（MUST。恒久的に人間ゲート（不可避）で担保する）。

* **認可欠落（missing authorization）**: エンドポイント・操作を「誰が実行してよいか」はビジネス上の意図であり、コード上は構文的に正常な分岐として現れます。静的解析は「認可チェックのコードが存在するか」は検出できても、「そのチェックが要求どおり正しいか」「そもそも必要な認可チェックが欠落していること自体」は意味的判断を要するため検出できません。
* **IDOR（Insecure Direct Object Reference）**: ある識別子への正当なアクセス範囲・所有者の妥当性はビジネス不変条件であり、コードの構文からは判定できません。
* **ビジネスロジック不備**: 処理そのものは技術的に正しく動作するが、業務要件と乖離している欠陥（例: 割引率の上限チェック漏れ、状態遷移の抜け穴、レート制限の意図しない迂回経路）は、要求仕様との照合を要するため静的解析の対象外です。

**SAST 導入をもって、上記の欠陥クラスを含む「網羅的」なセキュリティ検証が完了したと表現してはなりません（MUST NOT）。** SAST は、既知の脆弱性パターン（インジェクション・XSS・安全でないデシリアライズ・安全でない暗号利用等の構文・データフローパターン）に対する機械強制の一部を担うに過ぎず、認可・ビジネス不変条件の妥当性は人間レビュー・脅威モデリング・認可テストの併用によって担保しなければなりません（MUST）。
