# テスト標準（Testing Standards）

* Version: 0.2.0（Proposed / ドラフト）
* Date: 2026-07-05
* 上位規範: constitution.md（開発憲章「8. 機械的に検証可能なルール」「9. 完了条件」）

本書は、憲章8章が委譲する「テストカバレッジ最低基準」とテスト方針の正本（SSoT）です。憲章と矛盾する場合は憲章が優先します（MUST）。

## 1. カバレッジ最低基準（憲章8章「カバレッジが最低基準を満たすこと」の正本）

| 対象 | 行カバレッジ | 分岐カバレッジ | 強制 |
| --- | --- | --- | --- |
| リポジトリ全体 | 60%（段階的に引き上げ） | — | CI（`verify` ジョブ／`build.sh` の閾値オプション）※現状未実装。導入は採用組織（強制台帳 #15b） |
| 新規/変更コード（差分） | 80% | 70% | CI（diff-cover 等。導入は採用組織） |

> 上記は推奨初期値であり、採用組織がガバナンス決定で確定します。各スタックの閾値オプションへ反映すること
> （pytest `--cov-fail-under`、jest `coverageThreshold`、Go カバレッジ集計、JaCoCo ルール 等）。
> 段階導入プロファイル（development-process.md「8.」）に応じ初期値を緩めてよい（例: Lite=全体40%）。ただし 0%（無強制）にしてはなりません（MUST NOT）。

## 2. テスト方針

* TDD を基本とし、テストを実装より前に置きます。spec の機能要求（Given/When/Then）に対応づけます（SHOULD）。
* 認可・入力境界・PII の取り扱いは必ずテストで保証します（SHOULD）。テストは合成データのみを用い、本番 PII を AI／外部 AI に入力してはなりません（MUST NOT。security-standards.md「2.」）。
* フレークテストは検疫し、原因側を修正します。ゲート緩和で回避してはなりません（MUST NOT。憲章「自己修正ループの防止」）。

## 3. テストデータ（予約済み識別子の使用）

「2.」の合成データ原則を機械的に運用可能にするため、例示・テスト・spec のサンプル値には IETF が例示用に予約した識別子を用います。実在の識別子の混入は、PII/機密流出（security-standards.md「2.」）・外部への意図しない通信・環境依存フレークの原因になります。

* **ドメイン名**: RFC 2606 / RFC 6761 の予約名（`example.com` / `example.org` / `example.net`、TLD `.test` / `.invalid` / `.localhost`）を使わなければなりません（MUST）。実在ドメインを合成データに使ってはなりません（MUST NOT）。
* **メールアドレス**: 上記予約ドメインを用います（例: `hanako@example.com`）（MUST）。
* **IPv4 アドレス**: RFC 5737 の文書用ブロック（`192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`）を使わなければなりません（MUST）。
* **IPv6 アドレス**: RFC 3849 の文書用プレフィックス（`2001:db8::/32`）を使わなければなりません（MUST）。
* **電話番号等、IETF に予約枠がない識別子**: 実在し得ない値または各国の例示用番号帯を用い、採用組織の合成データ規約として本書に追記します（SHOULD）。
* **API エラーの契約テスト**: エラー応答は RFC 9457（Problem Details）形式であることを表明します（SHOULD。api-standards.md「3.」）。
* **日時・UUID**: テストフィクスチャの日時は RFC 3339、UUID は RFC 9562 表記に固定し、スナップショット比較を安定させます（SHOULD。coding-standards.md「3.」）。
