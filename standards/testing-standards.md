# テスト標準（Testing Standards）

* Version: 0.3.0（Proposed / ドラフト）
* Date: 2026-08-20
* 上位規範: constitution.md（開発憲章「8. 機械的に検証可能なルール」「9. 完了条件」）

本書は、憲章8章が委譲する「テストカバレッジ最低基準」とテスト方針の正本（SSoT）です。憲章と矛盾する場合は憲章が優先します（MUST）。

## 1. カバレッジ最低基準（憲章8章「カバレッジが最低基準を満たすこと」の正本）

| 対象 | 行カバレッジ | 分岐カバレッジ | 強制 |
| --- | --- | --- | --- |
| リポジトリ全体 | 60%（段階的に引き上げ） | — | CI（`verify` ジョブ／`build.sh` の閾値オプション）※現状未実装。導入は採用組織（強制台帳 #15b） |
| 新規/変更コード（差分） | 80% | 70% | CI（diff-cover 等。導入は採用組織） |

> 上記は推奨初期値であり、採用組織がガバナンス決定で確定します。各スタックの閾値オプションへ反映すること
> （pytest `--cov-fail-under`、jest `coverageThreshold`、Go カバレッジ集計、JaCoCo ルール 等）。
> 段階導入プロファイル（development-process.md「8.」）に応じ初期値を緩めてよい（例: Lite=全体40%）。ただし 0%（無強制）にしてはなりません（MUST NOT）。
> カバレッジは「テストが実行されたこと」の最低基準にすぎません。テストが実際に不具合を検出できることの基準は「4. テスト品質ゲート」を参照してください。

## 2. テスト方針

* TDD を基本とし、テストを実装より前に置きます。spec の機能要求（Given/When/Then）に対応づけます（SHOULD）。
* 認可・入力境界・PII の取り扱いは必ずテストで保証します（SHOULD）。テストは合成データのみを用い、本番 PII を AI／外部 AI に入力してはなりません（MUST NOT。security-standards.md「2.」）。
* フレークテストは検疫し、原因側を修正します。ゲート緩和で回避してはなりません（MUST NOT。憲章「自己修正ループの防止」）。

## 3. テストデータ（予約済み識別子の使用）

「2.」の合成データ原則を機械的に運用可能にするため、例示・テスト・spec のサンプル値には IETF が例示用に予約した識別子を用います。実在の識別子の混入は、PII/機密流出（security-standards.md「2.」）・外部への意図しない通信・環境依存フレークの原因になります。

* **ドメイン名**: RFC 2606 / RFC 6761 の予約名（`example.com` / `example.org` / `example.net`、TLD `.test` / `.invalid` / `.localhost`）を使わなければなりません（MUST）。実在ドメインを合成データに使ってはなりません（MUST NOT）。
* **メールアドレス**: 上記予約ドメインを用います（例: `hanako@example.com`）（MUST）。
* **IPv4 アドレス**: RFC 5737 の文書用ブロック（`192.0.2.0/24`・`198.51.100.0/24`・`203.0.113.0/24`）を使わなければなりません（MUST）。
* **IPv6 アドレス**: RFC 3849 の文書用プレフィックス（`2001:db8::/32`）を使わなければなりません（MUST）。
* **電話番号等、IETF に予約枠がない識別子**: 実在し得ない値または各国の例示用番号帯を用い、採用組織の合成データ規約として本書に追記します（SHOULD）。
* **API エラーの契約テスト**: エラー応答は RFC 9457（Problem Details）形式であることを表明します（SHOULD。api-standards.md「3.」）。
* **日時・UUID**: テストフィクスチャの日時は RFC 3339、UUID は RFC 9562 表記に固定し、スナップショット比較を安定させます（SHOULD。coding-standards.md「3.」）。

## 4. テスト品質ゲート（Mutation Score・Spec 由来・認可否定パス）

憲章「6. AIエージェント統治と自律境界」は、テストの追加・修正を AI エージェントの自律行為として許可しています（承認マトリクス）。一方で、「1.」が定めるテスト品質の唯一のゲートはカバレッジです。**同一エージェントが実装とテストの両方を書き、カバレッジのみで検証する構成は、検証が自己言及に陥ります**。実装のバグをそのまま反映したテストは、実装と一致する限りカバレッジを満たしてしまうため、そのバグを検出しません。

この論証は、憲章「10.1.7 UI 文書の役割分担」が Storybook についてすでに述べているものと同一の構造です。同節は「Storybook を『唯一のUI仕様』と位置づけてはならない（MUST NOT）。仕様と検証装置を同一視すると、実装に合わせて Story を書き換える経路が開き、検証が自己言及に陥る」と定めています。本節は、この論証をユニットテスト一般へ一般化するものです。カバレッジという「実行された」ことの確認だけでは、Story が実装に追従して書き換えられるのと同じ経路（テストが実装に追従して書き換えられる経路）を閉じられません。

> **休眠・活性化**: 本節は、リポジトリにコードスタックが導入され、自動テストが存在する状態で活性化します（`scripts/checks/build.sh` が「no code stack detected」を報告する間は休眠。憲章「8. ブートストラップ規定」と同趣旨）。コードスタック未導入の間は機械強制を行いませんが、本節の MUST は削除されたわけではなく、コードスタック導入時点から適用されます（AGENTS.md「8.」の UI 節が採用する休眠パターンと同じ設計）。

### 4.1 カバレッジと mutation score の関係

カバレッジと mutation score は同じ目的の指標ではありません。両者の役割を混同してはなりません（MUST NOT）。

* **カバレッジ（行・分岐）＝ 前提条件**: そのコードが**実行された**ことのみを示します。アサーションの有無を問いません。
* **mutation score ＝ 判定条件**: そのテストが実装の変異（バグ相当の改変）を**実際に検出できる**ことを示します。

例: 次の関数とテストを考えます。

```text
function isEligible(age) { return age >= 18; }

test("isEligible", () => {
  isEligible(20); // 呼び出すだけでアサーションが無い
});
```

このテストは `isEligible` の行を実行するため行カバレッジ 100% を達成しますが、戻り値を検証していないため、`>=` を `>` に変えても・`18` を `0` に変えても・戻り値を反転させても、テストは失敗しません。mutation score は 0% です。カバレッジは「テストが存在し実行された」ことの必要条件にすぎず、「テストが機能を検証している」ことを保証しません。

* 変更ファイルに対する mutation score が、「4.2」に定める最低基準を満たさなければなりません（MUST）。全体実行はコストが高いため、差分（変更ファイル）に限定してよい（MAY）。
* mutation score は、カバレッジ（「1.」）の**代替ではありません**。カバレッジ基準を満たした上で追加的に満たす判定条件です。カバレッジ基準を満たさないコードに mutation score 基準のみを適用してはなりません（MUST NOT）。
* mutation score が「4.2」の最低基準に満たないテストを、受入基準の充足根拠として使ってはなりません（MUST NOT）。

### 4.2 段階導入プロファイルごとの mutation score 初期値（未確定）

development-process.md「8. 段階導入プロファイル」の比較表と同じ形で、プロファイルごとの mutation score 初期値を定めます。**具体的な数値をAIが発明することは禁止されているため、すべて `TBD-HUMAN` とします**（憲章「10.1.3 推測の禁止」と同じ趣旨をテスト品質へ適用。「一般的には」「通常は」による補完を禁止）。

| 項目 | Lite | Standard（既定） | Regulated |
| --- | --- | --- | --- |
| mutation score 初期値（変更ファイル差分） | TBD-HUMAN | TBD-HUMAN | TBD-HUMAN |
| 適用対象・除外基準（生成コード・自明な getter/setter 等の扱い） | TBD-HUMAN | TBD-HUMAN | TBD-HUMAN |

未確定事項の一覧・必要な判断は [governance/proposals/gp-0006-test-quality-gates.md](../governance/proposals/gp-0006-test-quality-gates.md)「未解決事項」を参照してください。上表の値が確定するまで、本表を根拠に mutation score ゲートを「整備済み」の機械強制として扱ってはなりません（MUST NOT。憲章「8. ブートストラップ規定」）。

### 4.3 受入基準からのテストの導出（spec 由来）

受入基準に対応するテストは、`specs/<feature>/spec.md` のユーザシナリオ（Given/When/Then）・機能要求（FR-#）から導出しなければなりません（MUST）。実装を読んで書いたテストを、受入基準の充足根拠としてはなりません（MUST NOT）。

理由: 実装から逆算して書いたテストは、実装のバグをそのまま前提にしてしまい、「実装が spec の要求を満たしている」ことの独立した証拠になりません。これは本節冒頭で述べた自己言及の別の表れです。

具体例（本リポジトリのサンプル仕様より）: `specs/001-user-profile-export/spec.md` の US-3／FR-3、および `specs/002-account-deletion/spec.md` の US-3／FR-3 は、いずれも「他者のデータを取得・削除できない」という否定形の受入基準を定めています。この受入基準に対応するテストは、spec.md の当該 ID から先に導出できなければならず、実装コードを読んで初めて書けるものであってはなりません（TDD の趣旨。「2.」）。

テストコードまたはテストの説明文に、対応する FR-# / US-# を明記することを推奨します（SHOULD）。対応関係が追跡できない場合、レビューでの機械的な確認が困難になります。

### 4.4 認可を要するエンドポイントの否定パステスト

認可を要するエンドポイント（API・画面・バッチ処理を問わない）は、権限を持たない主体からのアクセスが拒否されることを検証するテストを備えなければなりません（MUST）。

* 「権限を持たない主体」には、未認証の主体、認証済みだが対象データの所有者でない主体、権限ロールが不足する主体を含みます。
* 具体例: `specs/001-user-profile-export/spec.md` FR-3（「要求者自身のデータのみを返し、他ユーザのデータを返してはならない」）、`specs/002-account-deletion/spec.md` FR-2（「要求者自身のアカウントのみを削除し、他ユーザを削除してはならない」）は、いずれも認可の否定パスです。対応するテスト（他ユーザとしての要求が拒否されることの検証）を欠いたまま実装を完了としてはなりません（MUST NOT）。

### 4.5 否定パステストの網羅性検証（設計案。実装は本書の対象外）

「4.4」は個々のエンドポイントに対する義務を定めますが、**すべての認可対象エンドポイントに漏れなく否定パステストが存在すること**（網羅性）は、個別テストの存在確認だけでは機械的に保証できません。新設エンドポイントの追加時にテストが追従し忘れられても、既存のゲート（カバレッジ・mutation score）はこれを検出しません。

本書は、この網羅性検証の**設計案**を示します（憲章「3. 基本原則」SSoT の既存パターン「生成物が正本と一致していることは、CIで生成処理を再実行し差分が無いことを検証することで機械的に確認できる」に整合）。**実装は本 WU（WU-05）の範囲外とし、governance/enforcement-ledger.md に人間ゲート（暫定）として登録します**（強制台帳 #39）。

設計の概略:

1. 採用スタックのルーティング定義（フレームワークのルータ・OpenAPI 定義等）を正本とし、そこから**ルート一覧を生成物**として出力する（例: `routes.generated.json`）。生成物は手編集しない（「10.1.1」と同じ SSoT パターン）。
2. 各ルートに認可要否のフラグを付与する（正本のルーティング定義側の注釈・デコレータ等から導出する）。
3. 認可必須なルートについて、対応する否定パステストの存在を、生成物とテストファイルの対応表として機械検証する。
4. 生成処理を CI で再実行し、生成物とルーティング定義の差分がゼロであることを確認する（生成物の手編集・追従漏れの両方を検出する）。

この設計は特定のルーティング実装・テストフレームワークを前提としません。採用スタックが決まった時点で、対応する `scripts/checks/` スクリプトとして実装するべきです（SHOULD）。
