# コーディング標準（Coding Standards）

* Version: 0.2.0（Proposed / ドラフト）
* Date: 2026-07-05
* 上位規範: constitution.md（開発憲章）

本書は、横断的なコーディング規約の正本（SSoT）です。憲章と矛盾する場合は憲章が優先します（MUST）。スタック固有の具体は採用時に確定します。

---

## 1. 整形・静的解析

* スタックごとにフォーマッタ／リンタを採用し、CI で強制するべきです（SHOULD）。
* 型チェックは可能な限り有効化するべきです（SHOULD。憲章8章「ビルドおよび型チェック」）。

---

## 2. 命名・構造・エラー処理

* 命名は意図を表すものとし、公開インターフェースは api-standards.md／architecture-standards.md に従うべきです（SHOULD）。
* 例外・エラーを握り潰してはなりません（SHOULD NOT）。秘密情報をログ・例外メッセージに含めてはなりません（MUST NOT。security-standards.md「3.」）。

---

## 3. データ表現（準拠 RFC・横断規約）

言語・スタックに依らず、境界（API・ログ・永続化・ファイル出力）を越えるデータは以下に従います。独自書式の新規導入は、ADR で理由を示さない限り行ってはなりません（MUST NOT）。

* **日時**: 内部処理は UTC を基準とし、境界では RFC 3339 形式で表現しなければなりません（MUST）。タイムゾーン省略・ローカル時刻前提・独自書式（`2026/07/05` 等）を新規に導入してはなりません（MUST NOT）。
* **UUID**: 識別子に UUID を用いる場合は RFC 9562（RFC 4122 の後継）に従います（MUST）。既定は v4。生成順ソートやインデックス局所性が必要な場合は v7 を選ぶべきです（SHOULD）。表記は小文字ハイフン区切りで統一します（SHOULD）。
* **バイナリのテキスト表現**: RFC 4648 に従い、URL・ファイル名・トークン文脈では base64url（パディングなし）を用いるべきです（SHOULD）。
* **JSON**: RFC 8259 に準拠し、交換用途では I-JSON（RFC 7493）の制約（UTF-8・重複メンバ禁止・IEEE 754 倍精度で安全な数値）に収めるべきです（SHOULD）。倍精度で表現できない数値（64bit 整数・金額の精密値等）は文字列で運びます（SHOULD。api-standards.md「3.」）。

> ねらい: データ表現の解釈揺れは、要件定義（曖昧語）・実装（変換バグ）・テスト（環境依存フレーク）の全工程で品質劣化を生みます。境界表現を RFC に固定することで、spec・契約・テストの記述を安定させます。
