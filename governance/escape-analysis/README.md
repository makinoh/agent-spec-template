# governance/escape-analysis/ — エスケープ欠陥の分類台帳（Escape Analysis）

* 上位規範: [constitution.md](../../constitution.md)「7. 変更管理」定期見直し／[development-process.md](../../development-process.md)「7. 緊急時例外（Break-glass）とインシデント対応」
* 変更クラス: **A**（統治・強制機構。CODEOWNERS＋権限影響ラベル必須）

本ディレクトリは、本番障害の事後レビュー（postmortem）で明らかになった各欠陥（**エスケープ欠陥** ＝ 品質ゲートをすり抜けて本番へ到達した欠陥）を記録する正本（SSoT）です。

## なぜこの台帳が必要か

[GP-0002](../proposals/gp-0002-machine-first-verification.md)（Machine-First Verification）は「機械検証で足りる範囲では人間ゲートを恒久化しない」を導入したが、この前提「機械検証で足りる」は**経験的仮説であり、反証可能な形で検証されなければ信念にとどまります**。本台帳は、本番障害が実際に発生するたびに「なぜすり抜けたか」を3分類で記録し、この仮説を継続的に検証する仕組みです（[GP-0008](../proposals/gp-0008-auditability-and-escape-analysis.md)）。

## 記録項目（各欠陥）

| 項目 | 内容 |
| --- | --- |
| 欠陥 ID | `ESCAPE-NNNN` |
| 概要 | 欠陥の事象・本番への影響 |
| 検出時期・経路 | いつ・どのように発覚したか（監視アラート／顧客報告／内部レビュー等） |
| 分類 | 次の3分類のいずれか（必須。複数の原因が絡む場合は主要因を選び、副次要因を備考に記載） |
| 該当ゲート・対応 | 分類 1・2 の場合: 整備すべきだった、または閾値を見直すべきだったゲートと具体的な対応 |
| オーナー・記録日 | 事後レビュー担当と記録日 |
| 関連 | 関連インシデント記録（[playbooks/incident-response.md](../../playbooks/incident-response.md)）・ADR・[enforcement-ledger.md](../enforcement-ledger.md) の行番号 |

### 分類（本番障害の事後レビュー時に必ずいずれかを付す。MUST）

1. **既存ゲートで検出可能だったが、ゲートが未整備だった** — 機械化していれば防げた欠陥。
2. **ゲートは存在したが、設定・閾値が不適切だった** — 既存ゲートの調整で防げた欠陥。
3. **現行技術では機械検出が不可能だった** — 意味的判断を要した欠陥。

> 分類の判定基準は constitution.md「3. 基本原則」検証手段の選択（構造的強制 → 機械強制 → 人間ゲート）と対をなします。分類 1・2 は「機械強制へ移行できたはずの人間ゲート（暫定）」、分類 3 は「機械強制へ移行できない人間ゲート（不可避）」の実例に対応します。

## 規約

- 本番障害の事後レビュー（[playbooks/incident-response.md](../../playbooks/incident-response.md)）を実施した場合、担当者は各欠陥を上記3分類のいずれかで本台帳に記録しなければなりません（MUST）。
- 分類は事後レビュー担当者による意味的判断であり、原理的に機械検証できません。台帳への記載有無・必須項目（分類・オーナー・記録日等）の充足は将来的に機械検証の対象にできますが、**分類そのものの正当性**は人間ゲート（不可避）(b) 責任の引受で担保します（[enforcement-ledger.md](../enforcement-ledger.md) #42）。
- **分類3の蓄積は、`人間ゲート（不可避）(a) 意味的判断` を新設・維持する正当化根拠として用いてよい（MAY）**。裏を返せば、分類3の実例が蓄積しない領域で「意味的判断だから」を理由に人間ゲートを維持し続けることは、本台帳による反証に晒されます。
- **分類1・2の蓄積は、機械強制整備の優先度根拠として用います（MUST）**。多発する分類1・2は、[enforcement-ledger.md](../enforcement-ledger.md) の該当行（または新規行）を「未整備」から機械強制整備の作業対象へ引き上げる入力とします。
- 本台帳は constitution.md「7. 変更管理」定期見直し（6ヶ月ごと、または重大インシデントの事後レビュー時）の入力に加えます（MUST。同章「定期見直し」参照）。
- 記録に本番の個人データ・顧客機密を含めてはなりません（MUST NOT）。欠陥の技術的性質と検出可能性の記述にとどめます。
- 個々の欠陥記録は [TEMPLATE.md](TEMPLATE.md) を複製して作成します（ファイル名は `escape-NNNN-<slug>.md`。risk-register の `RISK-NNNN` 命名規則に準じる）。

> **本リポジトリの現状（2026-08-20 時点）**: 本テンプレートは自己参照的な統治テンプレートであり、これ自体に本番運用・本番障害は存在しません。したがって本台帳には実例（`ESCAPE-NNNN` ファイル）がまだ0件です。[TEMPLATE.md](TEMPLATE.md) のみを置き、**架空の事例を実例として記載しません**（constitution.md「10.1.3 推測の禁止」と同じ「値を発明しない」原則に整合）。採用組織が本番障害を経験した時点で、事後レビューの一部として実例を追加してください。
