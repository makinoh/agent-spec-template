## 適用スコープ

- スコープ: project（本テンプレートを採用する個々のプロジェクト）
- 対象: 静的アセットの配信基盤、サーバ実行環境（必要な場合）、デプロイ方式
- 対象外: コンポーネント層の技術（[ADR-0003](adr-0003-storybook-astro-rendering.md)）、CDN キャッシュ戦略の詳細（standards/frontend-ui.md「7.」が正本）

## コンテキスト

### 背景

配信基盤の選定は、SSR の要否・エッジ実行の可否・バインディング（オブジェクトストレージ / KV / DB）の
有無を通じてアプリケーション構成に波及する。**後から変えると移行コストが大きい**ため、実装着手前に
決定する必要がある。

一方、Enterprise 採用では基盤が**組織の制約**（既存クラウド契約・データ所在地・監査要件・
オンプレ方針）で決まることが多く、テンプレート側で特定ベンダを前提にできない。

### 前提（Assumptions）

- 憲章「10.1」および standards/frontend-ui.md「1.〜7.」は基盤非依存であり、どの基盤でも成立する。
- 基盤に依存するのは設定の**書き方**のみ（`_headers` / CloudFront Function / nginx.conf 等）。

### 制約（Constraints）

- standards/frontend-ui.md「7.」の要求（キャッシュ制御・セキュリティヘッダ・CSP・再現性・ロールバック）は
  **基盤に関わらず満たさなければならない**（MUST）。
- **開発の性質が未確定のまま本 ADR を確定してはならない**（SSR の要否が決まらないため）。

## 意思決定事項

- 決定の問い: 静的アセットとサーバ処理をどの基盤で配信・実行するか。
- 含む: 本番・プレビュー環境の配信基盤、デプロイ方式。
- 含まない: キャッシュ戦略の具体値（standards/frontend-ui.md「7.」）、CI の実行基盤（GitHub Actions で固定）。

## 決定要因

- 組織の制約（既存契約・データ所在地・監査要件・オンプレ方針）
- SSR / エッジ実行の要否（ADR-0003 の決定と相互依存）
- 将来の動的処理（フォーム・認証・API）への拡張コスト
- ロックインの度合いと移行コスト
- 運用体制（Git 連携のプレビュー、権限管理、監査ログ）

## 評価観点

| # | 観点 | 重み | 判定基準 |
| --- | --- | --- | --- |
| 1 | 組織制約への適合 | 高 | 既存契約・データ所在地・監査要件を満たすか |
| 2 | 要求（frontend-ui「7.」）の充足 | 高 | キャッシュ制御・セキュリティヘッダ・CSP・再現性・ロールバックを満たせるか |
| 3 | 将来の動的処理への拡張性 | 中 | 再プラットフォームなしに拡張できるか |
| 4 | ロックインと移行コスト | 中 | 固有機能への依存度 |

## 検討項目

- 開発の性質（静的中心 / SSR 必須 / ハイブリッド）— **未確定なら本 ADR は確定できない**
- データ所在地・規制要件（個人データを扱うか、リージョン制約があるか）
- 既存のクラウド契約・IdP・監査基盤との接続
- プレビュー環境の要否と権限管理

## 選択肢

> 以下は代表例であり、網羅ではない。組織制約により他の基盤が唯一の選択肢になる場合もある。

### 選択肢 A：エッジプラットフォーム（Cloudflare Workers + Static Assets / Pages 等）

**メリット**: 静的配信と動的処理が同一ランタイム。エッジ実行で低レイテンシ。`_headers` で要求を素直に満たせる。
**デメリット**: 固有機能（バインディング等）への依存が進むとロックインが強まる。組織のクラウド契約と別系統になりうる。

### 選択肢 B：主要パブリッククラウドのマネージド配信（AWS S3+CloudFront / Azure Static Web Apps / GCP 等）

**メリット**: 既存契約・IAM・監査基盤に統合できる。データ所在地の制御が明確。
**デメリット**: ヘッダ制御やエッジ処理に追加コンポーネント（CloudFront Functions 等）が要る。構成が増える。

### 選択肢 C：ホスティング PaaS（Netlify / Vercel 等）

**メリット**: プレビュー環境と Git 連携が最も成熟。導入が速い。
**デメリット**: 企業の監査・データ所在地要件を満たせない場合がある。

### 選択肢 D：オンプレ / 社内 PaaS（コンテナ配信）

**メリット**: 組織の制約に確実に適合する。ロックインが最小。
**デメリット**: CDN・エッジ最適化・証明書運用を自前で担う。Lighthouse の性能要件を満たす作り込みが要る。

## 評価

> **本テンプレートでは加重評価を行わない。** 観点 1（組織制約への適合）が支配的であり、
> 組織の事情を知らずにスコアを付けることは推測（憲章「10.1.3」違反）にあたる。
> 採用プロジェクトが自組織の制約を入力したうえで、上記「評価観点」に沿って評価表を作成する。

## 決定（案）

- 採用する選択肢（案）: **保留**（採用プロジェクトが開発の性質と組織制約を確認したうえで確定する）
- 決定理由: 基盤選定は組織制約が支配的であり、テンプレート側で既定を置くと、その既定が
  検討を経ずに採用される危険がある。テンプレートが提供すべきは**選定の枠組みと基盤非依存の要求**であって、
  結論ではない。
- 不採用案の理由: 現時点で不採用と確定した案はない。
