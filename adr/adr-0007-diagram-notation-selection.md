## コンテキスト

### 背景

本プロジェクトでは、文書・図の SSoT はバージョン管理されたリポジトリに置き、外部ドキュメントツール上の文書は派生コピーとして扱う方針（standards/documentation-standards.md で新設予定）を採るにあたり、図についても「レンダリング済み画像のみを成果物とすることを禁じ、テキストまたは編集可能なソースファイルをリポジトリで管理する」という前提を置く。

この前提のもとで、本リポジトリが扱う図は性質の異なる 2 種類に大別できる。

1. **論理図**: シーケンス図・状態遷移図・フロー図・ER 図・C4 コンテキストレベル相当の図など、要素間の関係・遷移が情報の主眼となる図。
2. **物理構成図**: クラウドのネットワーク境界（Region / VPC / AZ / Subnet / セキュリティグループ等）の入れ子構造と、多数のサービス識別アイコンが情報の主眼となる図。

これまで本リポジトリはこの 2 種類に対して記法を固定していなかった。標準記法を確定しないまま図が増えると、GitHub 上でのレビュー時にレンダリングされない、外部ドキュメントツールへ複製した際に体裁が崩れる、といった問題が個別対応で積み上がるおそれがある。

### 前提（Assumptions）

- Mermaid は、GitHub の Markdown レンダラと、Wiki／ドキュメント管理系の外部ドキュメントツールの多くの両方で、追加のビルド・変換ステップなしにネイティブ描画に対応するとされる（個別ツールでの実際の描画可否、特に自動複製 API 経由で投入した場合の再現性は、本 ADR の時点で個別検証していない。当該論点は ADR-0008「前提」U-1 の対象であり、本 ADR の決定はこの一般的傾向を前提として用いるに留める）。これに対し PlantUML は、外部ドキュメントツール側ではプラグイン等を通じてネイティブに近い形で描画されることが多い一方、GitHub 側はネイティブ描画に対応しない。
- Mermaid のクラウドアイコンパックは、実行時の `registerIconPacks()` 呼び出しに依存する。静的な Markdown レンダラや、著者の JavaScript を実行しないホスト型レンダラは、この呼び出しを行えない。

### 制約（Constraints）

- Mermaid の `architecture-beta` は、ノードを固定グリッド上に配置する方式であり、辺のルーティングを行わない。ノード数がおおむね 8 を超える構成、または関係線が交差する構成では、可読性が急速に低下する。
- Mermaid は、リージョン／VPC／AZ／サブネット／セキュリティ境界のような多段の入れ子構造を安定的に表現できない。
- 物理構成図のレンダリングを担う方式は、いずれを選ぶにせよ、CI 上で決定的（deterministic）にレンダリングできることを、本 ADR の決定における前提条件とする（規範文言の正本は standards/documentation-standards.md「2.」）。レンダリング時に外部ネットワークからアイコン等のアセットを取得する方式は採らず、アイコン資産は固定バージョンでリポジトリ内にベンダリングする（本 ADR の決定自体がこの制約を満たす方式を選ぶ。「決定要因」参照）。
- 論理図と物理構成図の境界は、レビュー時に恣意的な解釈の余地なく判定できることを、本 ADR の決定における前提条件とする（規範文言の正本は standards/documentation-standards.md「2.」）。境界判定の精密な基準（レビューアが再現可能な基準）は同節を正本とし、本 ADR では再掲しない。要旨のみ述べれば、論理図は要素間の関係・遷移が情報の主眼である図、物理構成図はネットワーク境界の入れ子構造とサービス識別アイコンが情報の主眼である図、と区分する。

## 意思決定事項

- 決定の問い: 本リポジトリにおいて、論理図（シーケンス・状態遷移・フロー・ER・C4 コンテキストレベル相当）とクラウド物理構成図（ネットワーク境界の入れ子＋サービス識別アイコンが情報の主眼となる図）に、それぞれどの記法・レンダリング方式を標準として採用するか。
- 決定の範囲（含む）: 論理図の標準記法の選定。物理構成図の標準記法・レンダリング方式の選定（CI での決定的レンダリング、アイコン資産のベンダリング方針を含む）。
- 決定の範囲（含まない）: 文書・図を外部ドキュメントツールへ複製する可否・手順・複製物のメタデータ・ドリフト検知（ADR-0008 の対象）。論理図・物理構成図の境界判定の詳細な基準テキストそのものの文言（standards/documentation-standards.md「2.」の対象）。物理構成図レンダリングに用いる具体的なツール・製品の銘柄選定（本 ADR は方式のみを決定し、銘柄選定は採用組織が別途 ADR で行う。frontend-ui.md が配信基盤の銘柄選定を ADR-0004 に委ねるのと同型）。
- 期限・タイムボックス: 2026-09-05
- 未解決の問い（任意）: 物理構成図レンダリングの具体的なツールチェーン（描画エンジン・アイコン素材の入手元と版管理方法）は、本 ADR では確定しない。採用組織が自らの ADR で確定するまでの間、標準は方式（CI・決定的・ベンダリング）のみを拘束する。

## 決定要因

- GitHub 上と外部ドキュメントツール上の双方で、追加のビルド・変換ステップなしにネイティブ描画できること（前掲「前提」）。
- クラウドアイコンの表現が、実行時のアイコンパック登録に依存する方式に縛られないこと（静的・ホスト型レンダラでも成立すること）。
- 物理構成図（入れ子境界＋多数アイコン）が、ノード数や関係の複雑さの増加に伴って破綻しない表現力を持つこと。
- 論理図と物理構成図の記法選択の境界が、レビュー時に機械的・客観的に下せること（境界の精密な基準は standards/documentation-standards.md「2.」を正本とする）。
- 図のソースをリポジトリで管理し、レンダリング済み画像のみを成果物とすることを禁じる原則（documentation-standards.md が新設する SSoT 原則）と矛盾しないこと。
- 物理構成図のレンダリングが CI 上で決定的に行え、レンダリング時に外部ネットワークへ依存しないこと。

## 選択肢

> 各選択肢のメリット・デメリットは客観的・一般的事実として記載する。

### 選択肢 A：全図を Mermaid で統一する案

論理図・物理構成図の別を設けず、すべての図を Mermaid で記述し、GitHub・外部ドキュメントツールの双方でのネイティブ描画に統一する。

**メリット**

- GitHub 上で追加のビルド・変換ステップなしにネイティブ描画される。
- 単一の記法に統一されるため、学習・ツール導入コストが最小化される。
- テキストベースであり、Pull Request の差分としてレビュー可能（SSoT 適合性が高い）。

**デメリット**

- `architecture-beta` は固定グリッド上へノードを配置する方式で辺のルーティングを行わないため、ノード数がおおむね 8 を超える構成、または関係線が交差する構成では可読性が急速に低下する。
- リージョン／VPC／AZ／サブネット／セキュリティ境界のような多段の入れ子構造を安定的に表現できない。
- クラウドアイコンパックは実行時の `registerIconPacks()` 呼び出しに依存するため、静的・ホスト型レンダラでは利用できない場合がある。

### 選択肢 B：全図を PlantUML で統一する案

すべての図を PlantUML で記述する。外部ドキュメントツール側のネイティブ・プラグイン対応を活かす。

**メリット**

- 外部ドキュメントツールの多くでネイティブ・プラグイン経由で描画される。
- C4-PlantUML 等の拡張により、物理構成図でも一定の入れ子表現・アイコン利用が可能。
- テキストベースであり、SSoT 適合性が高い。

**デメリット**

- GitHub は PlantUML をネイティブ描画しないため、すべての論理図についてビルド・変換ステップ（レンダリングサーバまたは CI）が必須になる。これは「ビルド不要な記法を選ぶ」という論理図側の選定目的そのものに反する非対称性を生む。

### 選択肢 C：全図を draw.io で統一する案

すべての図を draw.io（diagrams.net）形式の GUI ツールで作成する。

**メリット**

- 入れ子境界・多数アイコンを含む物理構成図の表現力が高い。
- 業界標準級のアイコンステンシルが豊富に提供されている。

**デメリット**

- 保存形式が XML の構造化ブロブに近く、Pull Request の差分として人間が意味を読み取ることが実質的に困難であり、テキストベースの SSoT における差分レビューが機能しない。
- GitHub 上でネイティブ描画されず、レンダリング画像の別途添付が必要になる。

### 選択肢 D：作図 SaaS（例: Cacoo 等）に寄せる案

図の作成・保管を外部の作図 SaaS に寄せ、リポジトリには埋め込みリンクまたは書き出し画像のみを置く。

**メリット**

- GUI での共同編集・コメント機能など、SaaS 側の機能をそのまま活用できる。
- 外部ドキュメントツールとの貼り付け・埋め込み連携が提供されている場合がある。

**デメリット**

- 図のソース（編集可能な実体）がリポジトリ外の SaaS 内にのみ存在することになり、「文書・図の SSoT はバージョン管理されたリポジトリに置く」という原則と緊張関係を生む。
- 特定 SaaS への依存（ベンダーロックイン）が生じ、契約解除・移行時に図の再現性が失われるリスクがある。
- レンダリングが SaaS 側の可用性・仕様変更に依存するため、決定的（deterministic）な CI 再現が構造的に困難である。

### 選択肢 E：論理図は Mermaid、物理構成図は CI レンダリング（採用案）

論理図（シーケンス・状態遷移・フロー・ER・C4 コンテキストレベル相当）は Mermaid で記述し、GitHub・外部ドキュメントツールの双方でテキストのまま扱う。クラウド物理構成図（ネットワーク境界の入れ子＋サービス識別アイコンが情報の主眼となる図）は、テキストまたは編集可能なソースファイルをリポジトリで管理しつつ、レンダリングは CI 上で決定的に行い（アイコン資産は固定バージョンでベンダリングし、レンダリング時に外部ネットワークへアクセスしない）、レンダリング済み画像を成果物として提示する。

**メリット**

- 図の大多数を占める論理図についてはビルド不要の単一記法（Mermaid）に統一でき、GitHub・外部ドキュメントツールの双方で扱える。
- 物理構成図は入れ子境界・多数アイコンの表現力に優れた専用の記法・ツールで描画でき、選択肢 A で顕在化する Mermaid の制約（固定グリッド・多段入れ子の不安定さ・アイコンパックの実行時依存）を回避できる。
- 物理構成図についても、レンダリング済み画像ではなくテキスト／編集可能ソースをリポジトリで管理するため、「画像のみを成果物とすることを禁じる」原則と両立する。

**デメリット**

- 図の種類によって記法・ツールが 2 系統に分かれるため、単一記法へ統一する選択肢 A と比較して学習・運用対象が増える。
- 物理構成図については、CI によるレンダリングパイプライン（アイコン資産のベンダリング・pinning を含む）を新たに構築・保守する必要がある。

> 注: 「外部ドキュメントツール上でのネイティブ描画可否（3）」列のスコアは、個別ツールでの実測比較ではなく、前掲「前提」に述べた一般的傾向に基づく方向性の評価にとどまる。特に、自動複製 API 経由で投入した Mermaid フェンスがツール内部の保存形式変換を経てもなお復元・描画されるかという再現性は、ADR-0008「前提」U-1 が扱う未検証事項であり、本表はこれが解決済みであることを前提とした比較ではない。

**評価メモ（起案者による所見。レビューアは追記・修正してよい）**

> 選択肢 A は GitHub 側の描画・学習コスト・SSoT 適合性で最高評価だが、物理構成図の表現力で最低評価となり、加重合計では E に劣る。選択肢 E は単一記法（A）ほどの学習コストの低さは持たないものの、物理構成図の表現力と GitHub 側描画を両立し、加重合計で最高となる。E が全観点で最高評価というわけではない点（GitHub 描画は A と同点、外部ツール描画は B に劣る、学習コストは A に劣る）に留意して確認されたい。

## 決定（案）

- 採用する選択肢（案）: **E（論理図は Mermaid、物理構成図は CI レンダリング）**。起案者の提案は選択肢 E であり、人間承認により決定（案）から決定に確定する。
- 決定理由: 本リポジトリの図の大半を占める論理図については、ビルド不要でレビューしやすい Mermaid への統一が学習・運用コストと SSoT 適合性の両面で優れる。一方、物理構成図は Mermaid の `architecture-beta` が抱える構造的な制約（固定グリッド、多段入れ子の不安定さ、アイコンパックの実行時依存）により選択肢 A の対象から除外し、CI 上で決定的にレンダリングする別方式を割り当てる。この分割により、加重合計（60）が最も高くなるとともに、「画像のみを成果物とすることを禁じる」SSoT 原則を物理構成図についても満たす。
- 不採用案を選ばなかった理由: A は物理構成図の表現力で構造的に破綻する。B は GitHub 側のネイティブ描画を失い、論理図についてまでビルドステップが必要になる非対称性を生む。C は保存形式がテキスト差分レビューに適さない。D は図の SSoT がリポジトリ外に出てしまい、ベンダーロックインと非決定的レンダリングの問題を抱える。
- 前提条件・制約: 物理構成図のレンダリングパイプラインは、CI 上で決定的にレンダリングできること、レンダリング時に外部ネットワークからアイコン等のアセットを取得しないこと（アイコン資産は固定バージョンでベンダリングすること）を満たすことを、本 ADR の決定における前提条件とする（規範文言の正本は standards/documentation-standards.md「2.」）。論理図・物理構成図の境界判定の精密な基準は同節を正本とする。物理構成図レンダリングの具体的なツール・製品の銘柄選定は本 ADR の範囲外とし、採用組織が別途 ADR で確定する。
