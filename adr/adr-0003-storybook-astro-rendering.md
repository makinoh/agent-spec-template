## 適用スコープ

- スコープ: project（本テンプレートを採用する個々のプロジェクト）
- 対象: UI プリミティブの実装技術、メタフレームワークとの分離方針、Storybook 連携方式
- 対象外: デザイントークンの強制手段（[ADR-0005](adr-0005-css-token-enforcement.md)。決定済み・フレームワーク非依存）、配信基盤（[ADR-0004](adr-0004-cloudflare-deployment-target.md)）

### 階層型ガバナンスにおける位置づけ

憲章「10.1」は**フレームワークを固定しない**。本 ADR は採用プロジェクトが技術を確定するための
決定記録であり、テンプレート本体（憲章・standards の「1.〜7.」）はいずれの選択でも成立する。

## コンテキスト

### 背景

憲章「10.1.4」は「Story を持たないコンポーネントを作らない」ことを求め、「10.1.5」は差分判定を
視覚回帰・a11y テストの実行結果のみに委ねる。したがって**コンポーネントが Storybook に載ること**が
UI 品質ゲート全体の前提になる。

一方、メタフレームワーク固有形式（例: `.astro`）は Storybook が標準で描画できない場合がある。
この判断を保留したまま実装を始めると、コンポーネントを作った後に「Storybook に載せられないので
Story が書けない」ことが判明し、「10.1.4」を満たせないまま実装だけが進む。

さらに Enterprise 採用では、**フレームワーク／メタフレームワーク／クラウド基盤が案件ごとに異なる**。
特定技術を前提にコンポーネントを書くと、基盤変更時に UI 資産の全面書き直しが発生する。

### 前提（Assumptions）

- 視覚回帰・a11y 検査は Storybook のビルド成果物に対して実行する（standards/frontend-ui.md「4.」）。
- CSS は CSS Modules ＋ Stylelint で強制する（ADR-0005。フレームワーク非依存）。

### 制約（Constraints）

- 採用パッケージのバージョンは `plan.md` に固定して記録する（MUST）。
- **開発の性質（コンテンツ中心／業務アプリ／ハイブリッド）が未確定のまま本 ADR を確定してはならない**
  （standards/frontend-ui.md「1.」）。

## 意思決定事項

- 決定の問い: UI プリミティブを**どの技術で書き**、メタフレームワークから**どう分離するか**。
- 含む: コンポーネント層の実装技術、Storybook 連携方式、分離の有無。
- 含まない: メタフレームワークそのものの選定（本 ADR で併記してもよいが、性質確定が先）、配信基盤（ADR-0004）。

## 決定要因

- 憲章「10.1.4」「10.1.5」の前提（Storybook に載る）を満たせること
- **メタフレームワーク差し替え時の影響範囲**（Enterprise 採用の要件）
- 実装と検証対象の一致度
- 依存の保守性（公式サポート経路か、コミュニティ依存か）
- チームの既存資産・スキル

## 評価観点

| # | 観点 | 重み | 判定基準 |
| --- | --- | --- | --- |
| 1 | Storybook 公式サポート経路に載るか | 高 | 視覚回帰・a11y の基盤がコミュニティ追随に依存しないか |
| 2 | メタフレームワーク差し替えコスト | 高 | 基盤変更時、書き直しがページ層に限定されるか |
| 3 | 実装＝検証対象の一致 | 中 | Story で検証したものが本番と同一か |

## 検討項目

- 開発の性質（コンテンツ中心 / 業務アプリ / ハイブリッド）— **これが未確定なら本 ADR は確定できない**
- コンポーネント層の候補（React / Preact / Vue / Svelte / Web Components）
- メタフレームワークの候補（Astro / Next.js / Nuxt / SvelteKit / Remix / なし）
- ページ層の視覚回帰をどう担保するか（層分離を選ぶ場合）

## 選択肢

### 選択肢 A：メタフレームワーク固有形式で直接描画する（層を分離しない）

コンポーネントをメタフレームワーク固有形式（例: `.astro`）で書き、Storybook 側のアダプタで描画する。

**メリット**: 実装と検証対象が完全一致する。層が 1 つで済む。
**デメリット**: Storybook 連携がコミュニティ依存になりうる。**全コンポーネントがメタフレームワークに拘束される**ため、基盤変更時の影響が全面に及ぶ。

### 選択肢 B：コンポーネント層を分離する（メタフレームワークはページ・レイアウトに限定）

UI プリミティブをフレームワークコンポーネント（React / Preact / Vue / Svelte 等）で実装し、
メタフレームワークは Layout・Page・データ取得を担当する。

**メリット**: Storybook の公式サポート範囲。**基盤変更の影響がページ層に限定される**。
**デメリット**: 層が 2 つになる。ページ層は Storybook に載らないため、ページ単位の視覚回帰で補う必要がある。

### 選択肢 C：Web Components で実装する（最もフレームワーク非依存）

**メリット**: どのメタフレームワークからも利用できる。標準技術。
**デメリット**: Storybook・型安全性・SSR の利便がフレームワークコンポーネントより劣る。エコシステムが薄い。

### 選択肢 D：決定を保留する（ベースライン）

**メリット**: 誤った固定を避けられる。
**デメリット**: **実装に着手できない**（憲章「10.1.3」）。保留のまま実装すると 10.1.4 を満たせない。

## 評価

スコアは 1（劣る）〜 5（優れる）。重み: 高 = 3、中 = 2。

| 観点（重み） | A: 分離しない | B: 層を分離 | C: Web Components | D: 保留 |
| --- | --- | --- | --- | --- |
| Storybook 公式サポート（3） | 2 | 5 | 3 | — |
| 基盤差し替えコスト（3） | 1 | 5 | 5 | — |
| 実装＝検証の一致（2） | 5 | 3 | 4 | — |
| チーム適合（2） | 4 | 4 | 2 | — |
| **加重合計** | **27** | **44** | **36** | — |

## 決定（案）

- 採用する選択肢（案）: **B（コンポーネント層を分離する）を推奨する。ただし具体的な技術は未確定。**
- 決定理由:
  1. **基盤差し替えコストの局所化**が Enterprise 採用の要件に直結する。A は全コンポーネントが
     メタフレームワークに拘束され、基盤変更時の影響が全面に及ぶ。
  2. 憲章「10.1.4」「10.1.5」の前提（Storybook に載る）を、コミュニティ製アダプタの追随に
     依存せず満たせる。
  3. A の利点（実装＝検証対象の一致）は、ページ単位の Playwright スクリーンショットで補完できる
     （standards/frontend-ui.md「4.」）。C は基盤非依存性で並ぶが、Storybook・型安全性の利便が劣る。
- 不採用案の理由: A は基盤変更コストが過大。C はエコシステムの薄さが Story 網羅・型強制の運用を圧迫する。
  D は実装に着手できない。

- 採用パッケージとバージョンを `plan.md` に固定して記録する。
